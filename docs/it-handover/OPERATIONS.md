# Operations Runbook

## 1. Service management

| Action | Command |
|---|---|
| Status | `sudo systemctl status anyplace.service` |
| Start | `sudo systemctl start anyplace.service` |
| Stop | `sudo systemctl stop anyplace.service` |
| Restart | `sudo systemctl restart anyplace.service` |
| Enable at boot | `sudo systemctl enable anyplace.service` |
| Full health check | `/opt/anyplace/status.sh` |
| Live logs | `sudo journalctl -u anyplace.service -f` |
| Last 200 lines | `sudo journalctl -u anyplace.service -n 200 --no-pager` |

The unit restarts automatically after a crash and after a reboot. A stale
`/opt/anyplace/RUNNING_PID` is removed before start, so it cannot block recovery.
If the service enters `failed`, inspect `journalctl` before restarting; repeated
failures usually mean a missing secret, a database authentication problem, or a
bad staged build.

## 2. Health and monitoring

### 2.1 Endpoints

```bash
curl -fsS http://127.0.0.1:9000/api/health     # no database dependency
curl -fsS http://127.0.0.1:9000/api/version
curl -fsS https://<public-host>/api/health
```

`/api/health` is suitable for systemd, Nginx, and external uptime checks. It
returns success when the Play process is serving requests; it intentionally does
not fail on a database outage, so pair it with a database probe.

### 2.2 Database probe

```bash
mongosh -u anyplace_app -p '<password>' --authenticationDatabase admin anyplace \
  --eval 'db.runCommand({ping:1})'
```

### 2.3 Host checks

```bash
df -h / /opt /var
free -m
systemctl is-active mongod nginx anyplace.service
journalctl -u anyplace.service --since '-10 min' -p warning --no-pager
```

Alert on: service not active, health check failing, disk above 85%, database
unreachable, and repeated restart messages.

## 3. Logs

- Application: `journalctl -u anyplace.service`.
- Nginx access and errors: `/var/log/nginx/access.log`, `/var/log/nginx/error.log`.
- MongoDB: `/var/log/mongodb/mongod.log` (or the container log if MongoDB runs in
  Docker).
- Certbot: `/var/log/letsencrypt/letsencrypt.log`.

Log rotation is handled by journald and the distribution's logrotate rules.
Application logs never contain passwords or tokens; do not add request-body
logging that would change that.

## 4. User administration

### 4.1 First administrator

On a fresh database, register the first local account through
`POST /api/user/register`. The single-admin database index allows exactly one
account with `type: "admin"`.

### 4.2 Updating users

Administrators can update users with `POST /api/auth/user/update` using an admin
access token. Normal users can update their own name, username, email, and
password. Moderators can edit users but cannot create administrators.

### 4.3 Password reset without the old password

Use an administrator token and the update endpoint to set a new password. If no
administrator can log in, recovery requires database access:

1. Take a backup.
2. Generate a PBKDF2 hash with the application's current parameters, or
   temporarily promote a known account and use the API.
3. Never copy a hash from another deployment; salts are per user.
4. Record the recovery action in the operations log.

## 5. Mapping data administration

### 5.1 Editing content

1. Open `https://<public-host>/architect/` and log in.
2. Create or edit the building, floors, POIs, and connections.
3. Upload floorplans; the server stores the source and generates tiles.
4. Publish the space when it is ready. Unpublished spaces are hidden publicly.

### 5.2 Tiling

Tiles are generated by the tiler under `server/anyplace_tiler/`. Bulk tiling is
CPU and disk intensive; run it outside peak hours. Generated tiles are never
committed; they can be regenerated from the committed source images.

### 5.3 Restoring the committed dataset

```bash
cd /opt/anyplace
sudo MONGODB_USERNAME=anyplace_app MONGODB_PASSWORD='<password>' \
  scripts/restore-dataset.sh --floorplans-root /opt/anyplace/floorplans
```

This replaces the mapping collections with the committed snapshot, preserves
existing users, applies indexes, and copies floorplan sources. Use `--dry-run`
to validate without writing. Use `--reassign-owner <owner-id>` when the restored
buildings must be editable by a newly registered administrator.

### 5.4 Ownership

Only the owner, co-owners, and administrators can edit a space. After importing
data created under a different account, reassign `owner_id` on `spaces` and
`campuses` to the current administrator, or add the administrator as a co-owner
through the architect.

## 6. Backup

### 6.1 One-time setup

```bash
sudo mkdir -p /etc/anyplace/backup
sudo cp /opt/anyplace/server/database/admin/config.example.sh \
        /etc/anyplace/backup/config.sh
sudo chmod 600 /etc/anyplace/backup/config.sh
sudo editor /etc/anyplace/backup/config.sh
```

Set the MongoDB connection, `BACKUP_DIR=/var/backups/anyplace`, and optionally:

- `BACKUP_GPG_RECIPIENT` to encrypt archives. When set, the script refuses to
  leave a plaintext archive behind.
- `BACKUP_OFFHOST_TARGET` to copy archives off-host with rsync.
- `MAX_BACKUPS` for retention (default 14).

The admin scripts expect `config.sh` in the same directory
(`server/database/admin/config.sh`). Create it as a symlink or copy the
configuration there:

```bash
sudo ln -sfn /etc/anyplace/backup/config.sh \
  /opt/anyplace/server/database/admin/config.sh
```

### 6.2 Manual backup

```bash
sudo /opt/anyplace/server/database/admin/backup.sh
```

The script:

1. Dumps the database into a single gzip archive.
2. Validates the archive with `mongorestore --dryRun`.
3. Writes a manifest with per-collection document counts.
4. Optionally encrypts the archive and copies it off-host.
5. Updates `backup.latest` and prunes old archives.

An empty or failed backup fails the script and must not be treated as valid.

### 6.3 Scheduled backup

```bash
sudo cp /opt/anyplace/docs/deploy/anyplace-backup.service /etc/systemd/system/
sudo cp /opt/anyplace/docs/deploy/anyplace-backup.timer   /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now anyplace-backup.timer
systemctl list-timers anyplace-backup.timer
```

### 6.4 Verify a backup

```bash
ls -lh /var/backups/anyplace/
cat /var/backups/anyplace/backup.latest.manifest
sudo /opt/anyplace/server/database/admin/restore.sh backup.latest --dry-run
```

A restore drill into a scratch database is mandatory before relying on backups.

## 7. Restore and disaster recovery

### 7.1 Restore into the live database

```bash
sudo /opt/anyplace/server/database/admin/restore.sh backup.latest
sudo systemctl restart anyplace.service
curl -fsS http://127.0.0.1:9000/api/health
```

The restore script validates the archive, supports GPG-encrypted backups, and
can rename the target database with `--nsFrom`/`--nsTo`.

### 7.2 Disaster recovery on a new host

1. Provision Ubuntu 22.04 with the same package set and JDK.
2. Install and authenticate MongoDB on loopback.
3. Restore the latest backup.
4. Clone this repository to `/opt/anyplace`, install the unit, and configure
   `/etc/anyplace/anyplace.env` with the same secrets.
5. Restore floorplan sources and radiomaps from the backup or the committed
   snapshot.
6. Build, start, and verify `/api/health`, `/api/version`, and the web apps.
7. Repoint DNS and issue the certificate.

If the application secret is lost, existing sessions are invalidated but data is
unaffected. If the password salt and pepper are lost, legacy password hashes
cannot be verified; PBKDF2 hashes remain valid.

### 7.3 Recovery drill

At least once per quarter:

1. Restore the latest backup into a scratch database.
2. Compare document counts with the manifest.
3. Start a second application instance against the scratch database on a
   non-public port.
4. Fetch a space, search for a POI, and compute a route.
5. Record the time taken and any deviations.

## 8. TLS certificate renewal

Certbot installs a renewal timer automatically. Verify it:

```bash
sudo certbot renew --dry-run
systemctl list-timers | grep certbot
```

After renewal, Nginx reloads through the Certbot hook. If the hook is missing,
reload manually:

```bash
sudo nginx -t && sudo systemctl reload nginx
```

## 9. Troubleshooting

| Symptom | Likely cause | Action |
|---|---|---|
| `anyplace.service` fails immediately | Missing `APPLICATION_SECRET`, bad `JAVA_HOME`, or no staged build | Check `journalctl`, verify `/etc/anyplace/anyplace.env`, rebuild with `sbt stage` |
| 502 from Nginx | Play is down or not on `127.0.0.1:9000` | `systemctl status anyplace`, `ss -ltnp \| grep 9000` |
| 404 for web app assets | `server/public/` not built or staged | Rebuild web clients and re-run `sbt stage` |
| MongoDB authentication failure | Wrong `MONGODB_*` values or user not created | Verify with `mongosh`, compare with `/etc/anyplace/anyplace.env` |
| CORS error in browser | `cors.allowedOrigins` does not match the public origin | Update `server/conf/app.private.conf`, restart |
| Tiles missing after restore | Tiles are generated, not backed up as sources | Restore floorplan sources and regenerate tiles |
| Search returns nothing | Wrong `cuid`/`buid` or unpublished data | Check identifiers and `is_published` |
| Disk full | Backups, tiles, or logs | Check `df -h`, prune old backups, move backups off-host |
| Repeated restarts | Start limit reached | Fix the underlying error, then `systemctl reset-failed anyplace.service` |

## 10. Change management

- Take a verified backup before upgrades and data imports.
- Test schema and index changes on a scratch database first.
- Keep `server/database/init_schema.js` idempotent.
- Record every production change with date, operator, commit, and verification.
- Do not edit generated assets under `server/public/` or staged distributions by
  hand; rebuild from source.
- Do not commit runtime secrets, `server/conf/app.private.conf`, `config.sh`, or
  backup archives.
